Для float плоский путь `toFloatNanosFlat` (V4) выигрывает на `mixed` и на чистых наборах `lo`/`hi`, но на `integers` он вышел хуже V3. Я нашёл причину в самом коде вызова, и дело не в плоском пути: исправление есть ниже.

## Результаты

| набор | V1 | V3 | V4 (Flat) | V4 против V3 |
|---|---|---|---|---|
| clinger | 0,68 | 0,68 | 0,67 | 0% |
| lo_mid | 6,36 | 2,67 | 2,48 | −7% |
| lo_high | 6,88 | 2,53 | 2,47 | −2% |
| hi | 6,44 | 2,87 | 2,68 | −7% |
| integers | 7,65 | 5,50 | 5,86 | **+6,5%** |
| ties | 4,55 | 4,45 | 4,48 | 0% (шум) |
| mixed | 11,40 | 6,77 | 5,93 | **−12%** |

Относительно V1 Flat быстрее на 48% на `mixed`. Мой прогноз, что общий путь будет на 0,3–0,6 нс дороже частных на однородных данных, не оправдался: он оказался даже чуть быстрее, видимо, потому что в нём нет ветки по `sh` и меньше инструкций, чем в двух раздельных путях.

## Почему `integers` не улучшился

Я ожидал, что набор упадёт до ~2,7 нс, раз ветка `hi == 0` пропала. Но в коде вызова, который я предлагал, осталось:

```java
if (hi == 0 && Long.compareUnsigned(lo, FAST_MAX_SIG_F) <= 0)
```

C2 компилирует `&&` в две отдельные ветки. Это видно в ассемблере, который вы присылали: `test rdx, rdx; je` (hi == 0), а следом `cmp r9, 0x1000000; ja`. В `integers` у 54% значений `hi == 0`, у остальных нет, поэтому первая ветка остаётся почти монеткой, и штраф около 2,7 нс сохраняется. То же самое было в double. Поэтому мой прошлый вывод для double («одна ветка 37/63 не лучше двух») был неверен: ветка там тоже оставалась двойной.

Решение: объединить проверку в одно сравнение без короткого замыкания:

```java
// float: W < 2^24  <=>  hi == 0 && lo < 2^24
if ((hi | (lo >>> 24)) == 0) {
    v = (float) lo / 1e9f;
} else {
    v = FPRoundingFloat.toFloatNanosFlat(hi, lo);
}

// double: W < 2^53
if ((hi | (lo >>> 53)) == 0) {
    v = (double) lo / 1e9;
} else {
    v = FPRoundingDouble.toDoubleNanosFlat(hi, lo);
}
```

Граничные значения `W = 2^24` и `W = 2^53` при строгом `<` попадают в плоский путь, и это допустимо. Для float я проверил `toFloatNanosFlat` на всех W от 1 (3,8 млн значений, включая границы `2^b ± 2` и `hi == 0`), расхождений с `BigDecimal` нет. Для double плоский путь рассчитан на W ≥ 2^53 (длина ≥ 54 бит), и `2^53` в проверках теперь тоже участвует: расхождений нет.

Ожидаю, что на `integers` и `mixed` для float и для double разрыв сократится, но это предсказание, не измерение.

## Дополнительно

`toFloatNanosFlat` корректен для любого W ≥ 1: наименьшее значение 10^-9 далеко от границы нормальных float. Значит, можно вообще убрать Clinger-ветку и направлять все значения в плоский путь. Тогда класс `clinger` подорожает с 0,67 до ~2,5 нс (цена общего пути, это оценка), зато в `FPDecimal.toFloat()` не останется ни одной ветки по данным. Это стоит делать, только если Clinger-значения (до 2^24·10^-9 ≈ 0,017, то есть малые доли единицы) в ваших данных редки. Для double плоский путь рассчитан на W ≥ 2^53, и убрать там Clinger нельзя без изменения нормализации.

## Итог

1. Для float берите `FPRoundingFloat.toFloatNanosFlat`, для double — `FPRoundingDouble.toDoubleNanosFlat` (или `toDoubleNanosHiFlat` + `compute_float`, если класс `lo` у вас частый и идёт пачками).
2. Замените условие в `FPDecimal.toFloat()` и `toDouble()` на однократное сравнение, как выше, и повторите `integers` и `mixed`.
3. Уберите из `FPRounding` всё остальное (старые ветвистые методы, `roundNanos`, `toDoubleNanos`, `toFloatNanos`, `Math.scalb`), оставшиеся методы перенесите в основной класс.
4. Тесты через `FPDecimal` (`randomByBitLength`, `powerOfTwoBoundaries`, ничьи, `integerAmounts`) покрывают новые границы, особенно `2^24` и `2^53`: они уже входят в `powerOfTwoBoundaries` с отклонениями `±2`.
