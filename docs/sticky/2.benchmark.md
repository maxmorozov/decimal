Результаты довольно однозначные: **замена маски на сдвиг в V2 не ускорила основной путь конвертации. Наоборот, для всех тестов с&#x20;**`hi`**&#x20;она стабильно медленнее примерно на 5%.**

Сведём два прогона в средние значения:

| Набор      | Original, ns/op | V2, ns/op | Изменение V2 |
| ---------- | --------------- | --------- | ------------ |
| `clinger`  | 3,079           | 3,085     | +0,2%        |
| `lo`       | 5,260           | 5,517     | **+4,9%**    |
| `hi_left`  | 5,276           | 5,525     | **+4,7%**    |
| `hi_right` | 5,222           | 5,499     | **+5,3%**    |
| `hi_both`  | 5,233           | 5,512     | **+5,3%**    |
| `integers` | 0,669           | 0,665     | −0,6%        |
| `ties`     | 5,253           | 5,177     | −1,5%        |
| `mixed`    | 7,404           | 7,426     | +0,3%        |
| `bank`     | 3,103           | 3,060     | −1,4%        |

Положительное изменение означает замедление.

## **Что здесь особенно интересно**

**1. Замедление&#x20;**`hi_left`**,&#x20;**`hi_right`**&#x20;и&#x20;**`hi_both`**&#x20;очень стабильное.**

В обоих прогонах V2 проигрывает примерно одинаково. Это не похоже на случайный шум измерений. Более того, результаты `hi_left` и `hi_right` ухудшились почти одинаково, то есть проблема не связана с конкретным направлением нормализации.

**2.&#x20;**`lo`**&#x20;тоже замедлился, хотя обсуждаемая замена относится к&#x20;**`toDoubleNanosBranchless`**.**

Это важное наблюдение: если V2 меняет только этот участок, стоит проверить, не изменился ли машинный код соседних методов или не влияет ли на результаты расположение кода и профиль компиляции. В частности, JIT может по-разному встроить методы и распределить регистры.

**3.&#x20;**`mixed`**&#x20;практически не изменился.**

Вероятно, выигрыш или проигрыш на конкретном пути частично маскируется распределением данных по другим веткам.

**4.&#x20;**`ties`**&#x20;и&#x20;**`bank`**&#x20;немного улучшились, но это не компенсирует проигрыш на основных&#x20;**`hi`**-наборах.**

## **Почему более короткий ассемблер оказался медленнее?**

Это как раз хороший пример того, почему количество инструкций и размер машинного кода не определяют производительность.

Исходный вариант:

```
long lost = l0 & ((1L << t) - 1);
```

V2:

```
long lost = l0 << (64 - t);
```

В V2 действительно можно избавиться от последовательности `shift + decrement + and`. Но это не означает, что итоговая последовательность быстрее:

- меняется зависимость от вычисления `t`;
- меняется распределение регистров;
- сдвиг может попасть на критический путь;
- C2 может иначе распланировать соседние инструкции.

На Ryzen 7 9800X3D один дополнительный `AND` сам по себе вовсе не обязательно дороже, чем альтернативная организация сдвигов.

## **Мой вывод**

Я бы **оставил исходный вариант**. У V2 нет убедительного выигрыша ни в одном из основных тестов конвертации, а на `hi`-путях есть устойчивое ухудшение примерно на 5%.

При этом есть один нюанс: в бенчмарке оба метода находятся в одном классе, а JMH запускает их в рамках одного набора тестов. Для окончательного вывода я бы сделал ещё один эксперимент: запустить исходную и V2-реализацию отдельно, в разных сборках, чтобы исключить влияние совместной компиляции и профилирования.
