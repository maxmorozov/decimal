## Что показывает ассемблер

**1. `hi != 0 ? … : …` в V3 и V4 превратился в настоящий переход, а не в cmov.**

```
test rdx, rdx
jne  L
lzcnt r11, r8 ; mov r9d, 0x40 ; sub r9d, r11d ; jmp M     ; hi == 0
L: lzcnt r10, rdx ; mov r9d, 0x80 ; sub r9d, r10d         ; hi != 0
M:
```

В V1 и V2 тот же результат считается без ветвления: `lzcnt, shr 6, neg, and, add`, это два `lzcnt` и около 7 тактов по цепочке зависимостей.

В V3 и V4 цепочка короче: один `lzcnt` и `sub`, около 4 тактов. Поэтому на однородных данных, где переход всегда идёт в одну сторону, они быстрее на 0,2–0,4 нс (`lo` 4,81 против 5,22).

**2. На `mixed` этот переход непредсказуем.**

Среди элементов, дошедших до общего пути, `hi == 0` бывает только у `lo`, то есть примерно в 25% случаев. Доля таких элементов в `mixed` около 4/6, итого около 0,17 промаха на элемент. При цене промаха 15–20 тактов это 3 такта, около 0,8–1 нс.

Промах ещё и ломает перекрытие итераций в OoO. Это видно по сумме: взвешенное среднее чистых профилей для V1 около 4,1 нс, а `mixed` 7,4 нс. Те же 3,3 нс идут на уже существующие ветки `nanos == 0` и «clinger или нет», они одинаковы во всех версиях. У V3 добавка составляет примерно 4,5 нс, то есть лишний переход стоит около 1,2 нс на элемент. Выигрыш 0,2–0,4 нс на предсказуемых данных он с лихвой перекрывает.

**3. Способ вычисления `lost` почти не влияет на результат.**

- `lost = l0 << (64 - t)` в V2 и V3 вместо `l0 & ((1L << t) - 1)` убирает `mov ecx,1 / shlx / dec / and` (около 5 инструкций), а `64 - t` переиспользуется для `h0 << (64 - t)`.
- Выигрыша нет, а на `mixed` сдвиг чуть хуже в обеих парах (+0,26 и +0,16 нс). В паре V3 и V4 на чистых профилях он при этом лучше. Знак эффекта меняется, значит это порты и раскладка кода, а не алгоритм.
- `lost` не лежит на критическом пути: он готов задолго до `r` и присоединяется только в `x = lost | r`. Критический путь такой: nlz → sh → сдвиги → два умножения на обратное число (магическая константа `0x112e0be826d694b3`) → `drop` → `m` → экспонента. Поэтому число инструкций почти ничего не даёт.

**4. Деление на 5^9 JIT уже превратил в `imul` и `sar 0x11`.** Это хорошо. Остались лишние `sar 63; sub` для знаковой коррекции, потому что JIT не знает, что `cur < 2^44`. Они стоят по 1 такту на деление.

## Важная оговорка про сами дампы

Во всех четырёх файлах ветки `units < 0` и `nanos < 0` скомпилированы как uncommon trap (`unstable_if`). То же с переносом `++hi`. То есть это компиляция по профилю, в котором отрицательных значений не было. Метка 69–74 мс тоже слишком ранняя для настоящего `mixed`, где половина значений отрицательные.

Скорее всего, это первая компиляция (id 76), а в замере метод получил deopt и был перекомпилирован. Реальный горячий код надо смотреть в последней компиляции. Кроме того, в бенчмарке `toDouble` инлайнится в цикл `jmhStub`, и автономный nmethod лишь приближение. Тем более нужен более полный дамп (`-XX:+PrintCompilation`, `-prof perfasm`). В нём, вероятно, появится ещё один непредсказуемый переход по знаку (50/50 в `mixed`), одинаковый для всех версий. Он увеличивает общий фон, но разницу между версиями не объясняет.

## Что бы я выбрал

- Реальный профиль `bank` идёт по Clinger-пути, там все четыре версии равны (3,05–3,10). Выбор влияет только на редкие `lo` и `hi`.
- Если данные могут быть смешанными, берите V1: она самая быстрая на `mixed` и самая стабильная (разброс ±0,05, у V2 ±0,17–0,19).
- V3 оправдана, только если на практике `hi == 0` и `hi != 0` приходят большими однородными пачками.
- Идея для проверки: получить короткую цепочку V3 без перехода. Считать оба `lzcnt` параллельно и выбирать результат через cmov-подобное выражение, это около 5 тактов вместо 7. Если интересно, помогу набросать и прогнать.
