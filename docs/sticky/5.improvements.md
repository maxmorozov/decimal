Теперь дампы соответствуют `mixed`: ветки знака скомпилированы по-настоящему, а не как uncommon trap. Остались только трапы для `units == Long.MIN_VALUE` и переноса `++hi`, они в профиле действительно не встречаются.

## Как скомпилирован знак

Во всех четырёх версиях код одинаковый, знак живёт в регистре как флаг:

```
test r10,r10 ; jl  L1          ; units < 0
test r11d,r11d ; jl L1         ; nanos < 0
xor ecx,ecx ; jmp L2
L1: mov ecx,1
L2: test ecx,ecx ; je skip     ; ещё одна проверка того же флага
    neg r10 ; neg r11d
skip: ... вся арифметика ...
    test ecx,ecx ; je ret      ; и в третий раз в конце
    vxorpd xmm0, xmm0, [signmask]
```

C2 не превратил это в cmov: флаг нужен в двух местах, на входе и на выходе. В итоге получились три ветки по одному и тому же 50/50 событию. Вторая и третья хорошо предсказываются по истории от первой, так что реально непредсказуема одна (`jl` по `units`). Но она стоит около 0,5 промаха на элемент и есть во всех четырёх версиях.

## Что это меняет в прежних выводах

Ничего не опровергает, а закрывает вопрос про «фон» `mixed`. Для V1 набегает примерно так:

- знак: около 0,5 промаха на элемент;
- `nanos == 0`: около 0,17;
- clinger или нет: около 0,17.

Итого около 0,85 промаха на элемент при 15–20 тактах за промах и потере перекрытия итераций. Это согласуется с избытком в 3,3 нс над взвешенным средним чистых профилей.

Разница между версиями осталась прежней:

- V3 и V4 по-прежнему имеют `test rdx,rdx ; jne` с двумя `lzcnt`-плечами. Это ещё одна непредсказуемая ветка (около 25%) поверх уже существующих, поэтому они проигрывают V1 на `mixed` примерно на 0,8–1,2 нс.
- Вариант `lost` (маска или сдвиг) по-прежнему лишь меняет раскладку инструкций. На критический путь он не влияет.

## Что сейчас стоит упростить

Самый дорогой элемент — ветка знака. Ее можно убрать арифметикой. Конструктор `Decimal9` гарантирует одинаковые знаки у `units` и `nanos`, поэтому знак берётся из их побитового ИЛИ:

```java
long s = (units | nanos) >> 63;                 // 0 или -1
units  = (units ^ s) - s;
long n = ((long) nanos ^ s) - s;
// ... lo1 = units * 1e9, lo = lo1 + n, hi как раньше ...
double v = scaleToDouble(hi, lo);
return Double.longBitsToDouble(Double.doubleToRawLongBits(v) | (s & Long.MIN_VALUE));
```

Случай `units == Long.MIN_VALUE` обрабатывается раньше, так что `-units` безопасен. Результат положителен и не нулевой (в этой ветке `nanos != 0`), поэтому OR со знаковым битом эквивалентен `-v`, а `-0.0` не возникает. Ветки `nanos == 0` и clinger остаются, их убирать нечем.

Оценка выигрыша прикидочная: до 1,5–2 нс на `mixed`, то есть заметно больше, чем вся разница между V1 и V2. Это нужно измерить. После этого сравнение V1 и V3 стоит повторить, потому что фон ошибок предсказания уменьшится и вклад ветки по `hi` станет виден чище.
