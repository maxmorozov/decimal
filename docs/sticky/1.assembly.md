Я посмотрел `decimal9.asm`. В нём действительно присутствуют обе реализации, скомпилированные C2:

- `toDouble` — исходный вариант с `l0 & ((1L << t) - 1)`.
- `toDoubleV2` — вариант с `l0 << (64 - t)`.

**Математически замена корректна, поскольку&#x20;**`lost`**&#x20;используется исключительно для определения sticky-бита.** Но интереснее то, как HotSpot оптимизирует эти выражения.

### **1. В чём эквивалентность**

В первом варианте:

```
long lost = l0 & ((1L << t) - 1);
```

Остаются младшие `t` битов `l0`.

Во втором:

```
long lost = l0 << (64 - t);
```

Те же младшие `t` битов перемещаются в старшие разряды `long`.

Таким образом:

\\[ lost_1 \ne lost_2 \\]

в общем случае, но:

\\[ lost_1 = 0 \iff lost_2 = 0 \\]

При условии \\(1 \le t \le 40\\), которое гарантируется твоим алгоритмом.

Поскольку далее выполняется:

```
long x = lost | r;
long sticky = (x | -x) >>> 63;
```

оба варианта дают совершенно одинаковый результат.

### **2. Что получилось в машинном коде**

В обоих случаях HotSpot использует BMI2-инструкции `SHLX` и `SHRX` (переменные сдвиги без влияния флагов процессора).

**Исходный вариант (**`toDouble`**)**, участок по адресам `0x...ef88–0x...efb5`:

```
shlx    rsi, rcx, rbx
shrx    r11, rdi, rbx
shrx    rbp, rdx, rbx
dec     rsi
and     rsi, rdi

shl     rbp, 0x20
mov     r9d, 0x40
sub     r9d, ebx
shlx    r10, rdx, r9
or      r11, r10
```

Здесь:

- `shlx` вычисляет `1L << t`;
- `dec` вычитает единицу;
- `and` выделяет потерянные биты.

**V2 (**`toDoubleV2`**)**, участок `0x...e3fe–0x...e438`:

```
mov     ebx, 0x40
mov     r9d, 1
mov     ecx, 0x4b
sub     ecx, r8d
sub     ebx, ecx

shrx    rsi, rdi, rcx
shlx    r11, rdx, rbx
shlx    rbx, rdi, rbx
or      rsi, r11
shrx    rcx, rdx, rcx
```

Здесь потерянные биты получаются одной инструкцией:

```
shlx    rbx, rdi, rbx
```

То есть компилятор действительно использует преимущество второго представления: вместо последовательности `SHLX + DEC + AND` получается один сдвиг.

Есть, однако, нюанс: окружающий код тоже немного изменился. Поэтому нельзя просто сравнивать количество инструкций для вычисления `lost` отдельно.

### **3. Сравнение размеров машинного кода**

Из заголовков двух C2-методов:

| Показатель    | toDouble   | toDoubleV2 |
| ------------- | ---------- | ---------- |
| Main code     | 680 байт   | 672 байта  |
| Total nmethod | 1472 байта | 1464 байта |
| Разница       |            | −8 байт    |

V2 немного компактнее.

При этом последующая арифметика деления, вычисления sticky, округления и формирования double практически эквивалентна по структуре.

### **4. Есть ли смысл в замене?**

Я бы оставил V2.

Причины:

1. Вычисление `lost` действительно упрощается: вместо трёх зависимых инструкций используется один сдвиг.
2. V2 позволяет компилятору использовать уже необходимые величины для вычисления сдвигов при нормализации.
3. Итоговый машинный код немного компактнее.
4. Корректность не зависит от содержимого старших битов `lost`, поскольку используется только проверка на ненулевое значение.

Но есть важная оговорка: `SHLX` — это не бесплатная операция. У неё есть латентность и требования к execution ports. Теоретически выигрыш может оказаться небольшим или отсутствовать в зависимости от микроархитектуры.

**Мой вывод:** замена выглядит обоснованной не только с точки зрения исходного Java-кода, но и с точки зрения реально полученного C2 assembly. Это хорошая микрооптимизация, которую стоит сохранить, если JMH подтверждает хотя бы отсутствие регрессии.

Для окончательного решения я бы сравнил оба варианта на твоём Ryzen 7 9800X3D, причём отдельно измерил бы throughput и latency (через цепочку зависимых вызовов). Разница в несколько инструкций здесь вполне может оказаться заметной только в throughput-тесте.
