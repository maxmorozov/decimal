Теперь картина гораздо интереснее: **V3 — самый быстрый вариант для однородных наборов данных (**`lo`**,&#x20;**`hi_left`**,&#x20;**`hi_right`**,&#x20;**`hi_both`**,&#x20;**`ties`**), но заметно проигрывает на&#x20;**`mixed`**.** Похоже, здесь проявился классический компромисс между branchless-кодом и условным переходом.

## **1. Сравнение результатов**

Усреднил два прогона каждого варианта:

| Набор      | V1: branchless + mask | V2: branchless + shift | V3: branch + shift | V4: branch + mask |
| ---------- | --------------------- | ---------------------- | ------------------ | ----------------- |
| `clinger`  | 3,079                 | 3,083                  | 3,085              | 3,085             |
| `lo`       | 5,223                 | 5,507                  | **4,810**          | 4,965             |
| `hi_left`  | 5,230                 | 5,506                  | **4,911**          | 5,147             |
| `hi_right` | 5,200                 | 5,502                  | **4,907**          | 5,132             |
| `hi_both`  | 5,217                 | 5,504                  | **4,912**          | 5,133             |
| `integers` | 0,673                 | 0,666                  | 0,673              | 0,667             |
| `ties`     | 5,243                 | 5,173                  | **4,917**          | 5,011             |
| `mixed`    | **7,393**             | 7,647                  | 8,330              | 8,165             |
| `bank`     | 3,103                 | 3,061                  | 3,087              | 3,081             |

Все значения — ns/op.

По сравнению с V1, V3 ускоряет основные наборы:

- `lo`: примерно на 7,9%;
- `hi_left`: на 6,1%;
- `hi_right`: на 5,6%;
- `hi_both`: на 5,8%;
- `ties`: на 6,2%.

Но `mixed` становится медленнее примерно на 12,7%.

## **2. Почему V3 настолько быстрее**

V1:

```
int nlzHi = Long.numberOfLeadingZeros(hi);
int nlz = nlzHi + (-(nlzHi >>> 6) & Long.numberOfLeadingZeros(lo));
int sh = (128 - nlz) - NORM_BITS;
```

V3:

```
int bits = hi != 0 ? 128 - Long.numberOfLeadingZeros(hi)
        : 64 - Long.numberOfLeadingZeros(lo);
int sh = bits - NORM_BITS;
```

В V1 вычисляются два `numberOfLeadingZeros`, а затем выполняется дополнительная арифметика для выбора результата. В V3 второй `numberOfLeadingZeros` нужен только тогда, когда `hi == 0`.

Для наборов `hi_left`, `hi_right` и `hi_both` старшая часть числа ненулевая всегда. Поэтому второй `numberOfLeadingZeros(lo)` вообще не требуется.

Это позволяет сократить вычислительную работу и, вероятно, уменьшить длину критического пути.

Но есть обратная сторона: в V3 появляется зависимость от ветвления.

## **3. Что показывает сравнение V3 и V4**

Здесь особенно интересно, что V3 и V4 отличаются только вычислением `lost`:

- V3 использует `l0 << (64 - t)`;
- V4 использует `l0 & ((1L << t) - 1)`.

При этом V3 быстрее V4:

| Набор      | Преимущество V3 |
| ---------- | --------------- |
| `lo`       | 3,1%            |
| `hi_left`  | 4,6%            |
| `hi_right` | 4,4%            |
| `hi_both`  | 4,3%            |
| `ties`     | 1,9%            |

Это любопытно в контексте предыдущего эксперимента: там замена маски на сдвиг ухудшала результаты примерно на 5%.

Получается, что **стоимость этих двух способов вычисления&#x20;**`lost`**&#x20;сильно зависит от окружающего машинного кода**. Вероятно, дело не столько в стоимости отдельной инструкции, сколько в распределении регистров и расписании инструкций C2. Один вариант может лучше вписываться в конкретную последовательность операций.

Поэтому я бы не стал делать общий вывод, что сдвиг быстрее маски или наоборот. В данном случае V3 — победитель, но это преимущество относится к полной реализации.

## **4. Почему V3 проигрывает на&#x20;**`mixed`

Это, пожалуй, самое важное ограничение V3.

В `mixed` случайным образом перемешаны разные категории чисел. Для части значений `hi == 0`, для остальных `hi != 0`.

В результате условие:

```
hi != 0
```

становится плохо предсказуемым. Процессор вынужден регулярно ошибаться в предсказании переходов.

В V1 вычисления branchless, поэтому такого штрафа нет. Именно поэтому V1 выигрывает у V3 на `mixed`:

- V1: 7,393 ns/op;
- V3: 8,330 ns/op.

Разница — около 12,7%.

Это вполне согласуется с гипотезой о branch misprediction, хотя для окончательного подтверждения нужны аппаратные счётчики `branch-misses`.

## **5. Что бы я выбрал**

Зависит от ожидаемого распределения входных данных:

- Если практически все значения имеют `hi != 0` или практически все `hi == 0`, я бы выбрал V3.
- Если данные могут быть произвольной смесью, V1 выглядит предпочтительнее.
- Если важен именно типичный финансовый сценарий, стоит ориентироваться на `bank`: там все четыре варианта практически одинаковы.

При этом я бы не выбирал реализацию только по `mixed`: этот набор намеренно создаёт трудные условия для предсказателя переходов. Но и игнорировать его нельзя, если реальные входные данные действительно так распределены.

## **6. Какой эксперимент я бы сделал следующим**

Я бы посмотрел на ассемблер V1–V4, особенно на:

1. Как C2 реализует `hi != 0` в V3/V4: условный переход или `cmov`.
2. Сколько инструкций реально остаётся для вычисления `numberOfLeadingZeros`.
3. Не попадает ли вычисление `sh` на критический путь нормализации.
4. Как меняется распределение регистров вокруг вычисления `lost`.

Особенно полезно получить `perf stat` для V1 и V3 с аппаратными событиями:

- `cycles`
- `instructions`
- `branches`
- `branch-misses`

Это позволит отделить выигрыш от уменьшения количества инструкций от штрафа за ошибочные предсказания.

**Мой предварительный фаворит — V3 для специализированного быстрого пути и V1 для универсального пути.** Но прежде чем вводить два варианта, я бы проверил реальные распределения входных данных и ассемблер V3.
