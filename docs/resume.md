Для банковских данных выбор проще, чем кажется по синтетическим наборам: почти всё ваше будет идти по Clinger-пути, и тонкая разница между версиями плоского пути для вас практически не важна.

## Какие классы данных у вас будут

Оценки по порядку величин: W = units·10^9 + nanos.

| данные | типичное W | класс double | класс float |
|---|---|---|---|
| курсы валют (0,9…200, до 6 знаков) | 10^9…10^11 | Clinger (W < 2^53 ≈ 9·10^15) | округление (W ≥ 2^24) |
| цены | до 10^15 | Clinger | округление |
| суммы контрактов до ~9·10^6 | до 9·10^15 | Clinger | округление |
| суммы до ~1,8·10^10 (в основном lo) | до 1,8·10^19 | плоский путь | округление |
| номиналы в JPY, KRW, IDR выше 1,8·10^10 | выше 2^64 | плоский путь (hi) | округление |

Для double Clinger по моей оценке составит порядка трёх четвертей значений, остальное редкие большие суммы. Для float Clinger почти не встретится (W < 2^24 это значения до 0,017), всё пойдёт через округление, но класс будет один (`lo`), то есть ветки предсказуемы. Другое следствие: значения вроде `1,0853` или `1250,75` содержат хвостовые нули в `nanos`, поэтому остаток деления на 5^9 у них иногда нулевой (при двух знаках после запятой примерно в 4% случаев), и случайной «монеты» из ваших `integers` у вас почти не будет.

## Что я бы выбрал

**V5 для обоих типов** (`(hi | (lo >>> N)) == 0` плюс `toDoubleNanosFlatBranchless` / `toFloatNanosFlatMask`). Причины:

- Цена бесветочности (+0,3–1,0 нс в предсказуемых классах) приходится на редкий класс, а выигрыш в непредсказуемых случаях страхует от перемешанных потоков.
- Код проще: одна проверка и одна функция на тип, без `compute_float` и его таблиц Эйзеля-Лемира.
- Время почти не зависит от значения, что удобно для предсказуемости задержек.

В масштабе RPC-фреймворка 3–5 нс на конвертацию это ничто рядом с сериализацией и сетью (микросекунды). Поэтому дальнейшая микрооптимизация вряд ли даст видимый эффект, а ошибки округления дадут. Я бы остановился.

## Что ещё стоит выяснить, по важности

1. **Корректность на границах и тестовое покрытие.** Прогнать `FPDecimalRoundingTest` на итоговом `FPDecimal` (в том числе `negative = true`) и убрать все лишние методы из `FPRoundingDouble` и `FPRoundingFloat`. Это главное, остальное вторично.
2. **Отрицательный ноль.** `FPDecimal(true, 0, 0)` сейчас даст `-0.0`. Для банковских клиентов это может быть неожиданно (`-0.0 == 0.0`, но `Double.equals` и форматирование различают). Решите, нормализовать ли ноль в конструкторе (проще и без стоимости в горячем пути) или в `toDouble()`.
3. **Реалистичный набор для бенчмарка.** Раз реальных данных нет, добавьте синтетический профиль, близкий к вашему:

```java
case "bank" -> bank(rnd);

private static long[] bank(Random rnd) {
    int r = rnd.nextInt(100);
    if (r < 55) {                                         // FX rates and prices, 4..6 decimals
        long units = rnd.nextInt(r < 20 ? 3 : 200_000);
        int digits = 4 + rnd.nextInt(3);
        int scale = (int) Math.pow(10, 9 - digits);
        return new long[]{units, (long) rnd.nextInt((int) Math.pow(10, digits)) * scale};
    } else if (r < 95) {                                  // amounts with 2 decimals, up to ~3e10
        long units = Math.floorMod(rnd.nextLong(), 1L << (10 + rnd.nextInt(26)));
        return new long[]{units, rnd.nextInt(100) * 10_000_000L};
    } else {                                              // large notionals without decimals
        return new long[]{Math.floorMod(rnd.nextLong(), 1L << (30 + rnd.nextInt(33))), 0};
    }
}
```
   Добавьте его в `@Param` обоих бенчмарков и сравните V1, V4 и V5. Если V5 не хуже V4 на этом наборе, вопрос закрыт.
4. **Clinger-путь для double.** Тут надо поправить мой прошлый вывод. Я сказал, что гипотеза о ложной зависимости не подтвердилась, но микробенчмарк (цикл по `long[]`) JIT, скорее всего, разворачивает с разными регистрами, поэтому он цепочку просто не воспроизводит. Корректный тест: временно заменить в `FPDecimalV5.toDouble()` Clinger-строку на `v = (Double.longBitsToDouble(0x4330000000000000L | lo) - 0x1.0p52) / 1e9;` (верно только для `lo < 2^52`) и прогнать `clinger` на данных до 52 бит. Если время упадёт с 3,07 до ~1 нс, в циклах конвертации массивов (например, ряд цен) выигрыш реальный. Для вас это самый частый путь, поэтому здесь потенциальная польза максимальна, но только если клиенты конвертируют массивы в цикле, а не по одному значению.
5. **Другие CPU и JDK.** Если клиентский код будет работать на других процессорах (Intel, ARM) или JDK, цена промаха предсказателя и решения C2 по `cmov` будут иными. На ARM стоит проверить хотя бы корректность и порядок величин.
6. **Нужен ли вам float.** Для денег он практически бесполезен (24 бита это около семи значащих цифр), и если API его не обещает, можно не поддерживать `toFloat()` вовсе и не нести его код.

Отдельно: в банковском API стоит прямо написать в документации, что `toDouble()` и `toFloat()` округляют по IEEE 754 (к ближайшему, при равенстве к чётному) и совпадают с `BigDecimal.doubleValue()`. Суммы и курсы лучше хранить и считать в `Decimal`, а `double` оставить для отображения и аналитики.
