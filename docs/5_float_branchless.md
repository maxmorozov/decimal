Скорость осталась прежней: v3 совпадает с v1 на `one_step` (265,6 и 265,4) и на `two_steps` (281,9 и 282,0). Это ожидаемо, ведь ветки в бенчмарке и так предсказывались идеально. Разница на `fast_path` (246 против 253) повторяет v2, где `roundFloat` тоже менялся, а на этом пути он не вызывается. Это снова шум от расположения кода, а не эффект правки.

## Главное в ассемблере: код всё равно не бесветочный

Я обещал, что округление через `add` избавит от ловушек. Ассемблер показывает, что это не так: в v3 по-прежнему две `uncommon trap`.

- `cmp r11, r10; je` сразу после умножения. Это `w == q * D5_9`, то есть остаток равен нулю. Профиль бенчмарка ни разу не видел такого значения, и C2 заменил ветку ловушкой. После этого он считает `sticky` всегда истинным (`or r8d, 1`).
- `test r8d, r8d; je` — это `sticky ? 1 : 0`. Тернарный оператор по `boolean` C2 скомпилировал в ветку, а не в `setcc`/`cmov`, и ложная ветка тоже стала ловушкой.

То есть горячий путь действительно без ветвлений, но только потому, что бенчмарк «подсказал» C2 исход. Код сам по себе от профиля не независим.

## Почему это важно именно для ваших данных

В бенчмарке остаток от деления всегда ненулевой, и ничьих нет. В реальных данных это не так. Если `nanos == 0`, то `W = units · 10^9` делится на `5^9`, и остаток при сдвиге влево равен нулю. Значит, все целые суммы дают `sticky == false`. Первое такое значение вызовет деоптимизацию и перекомпиляцию. Дальше есть два варианта:

- если данные по большей части одного типа, всё останется предсказуемым и быстрым;
- если целые и дробные значения перемешаны, C2 либо получит непредсказуемые ветки (промахи по ~15–20 тактам), либо сам сгенерирует `cmov`. На что именно он решится, предсказать заранее нельзя.

Поэтому профильному бенчмарку, где остаток всегда ненулевой, доверять нельзя. Добавьте режим, где часть значений имеет `nanos == 0`, и замерьте v1 и вариант ниже.

## Бесветочный вариант

Нужно убрать `boolean`-тернарий и сравнение `!=` и считать `sticky` арифметикой. Для этого `roundFloat` принимает потерянные биты как число, а не как `boolean`:

```java
public static float toFloatNanosHi(long hi, long lo) {
    int sh = (128 - Long.numberOfLeadingZeros(hi)) - NORM_BITS_F;
    long w = (lo >>> sh) | (hi << (64 - sh));
    return roundFloat(w, lo & ((1L << sh) - 1), sh);            // lost bits as is, without "!= 0"
}

public static float toFloatNanosLo(long lo) {
    int sh = (64 - Long.numberOfLeadingZeros(lo)) - NORM_BITS_F;
    if (sh > 0) {
        return roundFloat(lo >>> 1, lo & 1, sh);
    }
    return roundFloat(lo << -sh, 0, sh);
}

private static float roundFloat(long w, long lost, int shift) {
    long q = w / D5_9;
    long t = (w - q * D5_9) | lost;                           // non-zero <=> sticky
    long sticky = (t | -t) >>> 63;                            // 0 or 1, without branches

    int drop = MANTISSA_DROP_F + (int) (q >>> Q_MIN_BITS_F);
    long half = 1L << (drop - 1);
    long add = half - 1 + (((q >>> drop) | sticky) & 1);
    long m = (q + add) >>> drop;

    int p = drop + shift - EXP_SHIFT;
    return Float.intBitsToFloat((int) (((long) (p + EXPONENT_OFFSET_F) << MANTISSA_EXPLICIT_BITS_F) + m));
}
```

Проверка выражения `(t | -t) >>> 63`: для `t == 0` результат 0, а для `t > 0` старший бит `-t` равен 1. Здесь `t < 2^31`, поэтому проблем со знаком нет. Остальные рассуждения про `add` остаются верными. Ветка `if (sh > 0)` в `toFloatNanosLo` зависит от значения, но она срабатывает только при `lo ≥ 2^63`, то есть почти никогда.

Тот же приём годится для `toDoubleNanosHi`: там `sticky` из `sh > 0` и `r != 0` можно собрать так же, а округление записать через `add`. Саму ветку `sh > 0` вместо `else` убрать сложнее, и она зависит от длины числа. Если длины в ваших данных различаются, это отдельный источник промахов. Сначала проверьте на float.

## Тесты

Существующие тесты покрывают округление, но случай «остаток ноль, ничьей нет» (целые суммы) в них представлен слабо: в `randomUnitsAndNanos` нулевой `nanos` почти не встречается. Добавьте:

```java
/** nanos == 0: W делится на 5^9, остаток нулевой, sticky только от сдвига. */
@Test
void integerAmounts() {
    Random rnd = new Random(SEED + 5);
    for (int i = 0; i < 200_000; i++) {
        long units = rnd.nextLong() >>> (1 + rnd.nextInt(63));
        check(BigInteger.valueOf(units).multiply(E9));
        check(BigInteger.valueOf(units).multiply(E9).add(BigInteger.valueOf(rnd.nextInt(1000)))); // рядом
    }
}
```

## Итог

Скорость не изменилась, и выбор между v1 и v3 по бенчмарку не определить. Я бы взял бесветочный вариант (последний листинг): он не зависит от того, что видел профиль, и он единственный, где я могу объяснить поведение на смешанных данных. Но решать стоит по новому замеру на смешанных данных, а не по текущему. Что касается деления: на Ryzen 9800X3D `div r64` быстрый, поэтому v2 почти не проиграла. Это объясняет малую разницу, но на других процессорах картина может отличаться, так что магическое умножение (v1/v3) остаётся более безопасным выбором.
