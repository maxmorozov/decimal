Да, и для float выигрыш больше, чем просто «чуть короче»: деление сводится к одному.

## Минимальная длина

Для корректного округления в `q = floor(W'/D)` должно быть минимум `precision + 1` бит: мантисса плюс бит округления. Всё, что ниже, покрывается sticky из остатка и из отброшенных при сдвиге бит. Если `W' ∈ [2^(N−1); 2^N)`, то нижняя граница `q` равна `2^(N−1)/D`. Нужно, чтобы она была не меньше `2^precision`:

```
2^(N-1-precision) ≥ D = 5^9,   D < 2^21   =>   N = precision + 22
```

- double: N = 75 (`q` имеет 54 или 55 бит)
- float: N = 46 (`q` имеет 25 или 26 бит)

Здесь я должен поправить себя. Раньше я писал, что 76 — минимальное значение, а при 75 `q` перестаёт быть двузначным. Это было неверно: при N = 75 длина `q` равна 54 или 55, это тоже две возможности, и `drop = 1 + (q >>> 54)` работает. Для double N = 75 можно взять, но выигрыша это не даёт: 75 бит всё равно не помещаются в `long`, и два деления остаются. Менять 76 на 75 ради этого я бы не стал.

## Float: одно деление и нет ветвлений

При N = 46 нормализованное `W'` помещается в один `long`. Раз `hi != 0`, то `bits ∈ [65; 93]`, и сдвиг `sh = bits − 46 ∈ [19; 47]` всегда положителен. Поэтому не нужна ветка «сдвиг влево», не нужен `h`, а деление `w / D` одно:

```java
/** (hi:lo) * 10^-9 -> float, hi != 0, round-half-even. */
public static float toFloatNanosHi(long hi, long lo) {
    int sh = (128 - Long.numberOfLeadingZeros(hi)) - 46;      // 19..47, всегда > 0
    long w = (lo >>> sh) | (hi << (64 - sh));                 // W' = W >>> sh, 2^45 <= W' < 2^46
    boolean sticky = (lo & ((1L << sh) - 1)) != 0;            // потерянные биты лежат только в lo

    long q = w / D5_9;                                        // [2^24; 2^26): 25 или 26 бит
    sticky |= w != q * D5_9;                                  // остаток деления != 0

    int drop = 1 + (int) (q >>> 25);                          // len(q) - 24 = 1 или 2
    long m = q >>> drop;                                      // 24 бита
    long rem = q & ((1L << drop) - 1);
    long half = 1L << (drop - 1);
    if (rem > half || (rem == half && (sticky || (m & 1) != 0))) m++;

    int p = drop + sh - 9;                                    // m * 2^p, p ∈ [11; 40]
    return Float.intBitsToFloat((int) (((long) (p + 149) << 23) + m));
}
```

Проверка границ:

- `hi << (64 − sh)`: `hi` имеет `bits − 64 ≤ 29` бит, после сдвига на `64 − sh` получается `bits − sh = 46` бит, то есть переполнения нет, и сдвиг в `W'` не теряет старших бит. Потери только в младших битах `lo`, и они попадают в `sticky`. Так как `sh ≤ 47 < 64`, этих битов хватает.
- `q`: `2^45/D > 2^24` (потому что `D < 2^21`), а `2^46/D < 2^26` (потому что `D > 2^20`). Поэтому `q ∈ [2^24; 2^26)`, то есть 25 или 26 бит.
- `m` после `drop`: 24 бита в обоих случаях (25 − 1 и 26 − 2), перенос `m == 2^24` обрабатывается сложением в `intBitsToFloat`, как и раньше.
- Экспонента: поле `p + 150 ∈ [161; 190] < 255`, субнормалов и переполнения нет.

Реальное ускорение я не измерял. По структуре кода оно должно быть заметным: одно деление вместо двух зависимых, ни одной непредсказуемой ветки по `sh`. Результат стоит перепроверить на `toFloat`-бенчмарке.

## Тесты

Ранее написанные `floatTies`, `roundingCarry` и `randomByBitLength` покрывают новый код без изменений: они вызывают `FPDecimal.toFloat()`. Инварианты для проверки констант можно записать общей формулой:

```java
@Test
void normalizationInvariants() {
    BigInteger d = BigInteger.valueOf(1_953_125L);
    for (int[] c : new int[][]{{53, 75}, {24, 46}}) {        // {precision, N}, N = precision + 22
        int precision = c[0], n = c[1];
        BigInteger lo = BigInteger.ONE.shiftLeft(n - 1).divide(d);
        BigInteger hi = BigInteger.ONE.shiftLeft(n).subtract(BigInteger.ONE).divide(d);
        assertEquals(precision + 1, lo.bitLength());          // есть бит округления
        assertEquals(precision + 2, hi.bitLength());          // длина q двузначна
    }
    assertTrue(BigInteger.ONE.shiftLeft(46).bitLength() <= 63);  // float: W' помещается в long
}
```

Если N уменьшить ещё на единицу, первая проверка упадёт: `q` может потерять бит округления, и результат перестанет быть корректным.
