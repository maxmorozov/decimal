Нужны значения, которые проходят через все ветки кода, и в тех же пропорциях, что в продакшене. C2 строит код по профилю: ветку, которой не было при прогреве, он заменяет на `uncommon trap`. Поэтому на прежних листингах была видна «идеальная» версия кода, а не та, что выполняется на реальных данных. Это же объясняет, почему в v3 пропало сравнение остатка: профиль не знал о нулевом остатке.

## Что должно быть в цикле

| что | пример `(units, nanos)` | какую ветку покрывает |
|---|---|---|
| Clinger | `(0, 5_000_000)` | `lo ≤ 2^24`, округление не вызывается |
| `lo_mid` | `(9007552, 144953729)` | левый сдвиг в `toFloatNanosLo` |
| `lo_high` | `(18055623887, 999999999)` | правый сдвиг на 1 бит, `lost = lo & 1` |
| `hi` | `(868298182114, 104073920)` | `toFloatNanosHi` |
| целые, остаток 0 | `(9_000_000, 0)`, `(10_000_000_000, 0)`, `(1234567890123, 0)` | нулевой остаток и `sticky == 0` на всех трёх путях |
| ничьи | `(16777217, 0)`, `(16777219, 0)`, `(16777217L << 20, 0)` | `rem == half` при чётном и нечётном `m`, на `lo` и на `hi` |
| округление вверх с переносом | `(33554431, 0)` | `m == 2^24` |

Значения `lo_high` и `hi` в `nanos`-вариантах нужно брать и с нулевой дробной частью, и с ненулевой, иначе C2 всё равно срежет ветку. Важно ещё, чтобы значения шли в случайном порядке, а не блоками. Иначе компилятор увидит «сначала только одно, потом только другое» и может выбрать другую раскладку.

Проще всего не перечислять значения вручную, а взять данные из бенчмарка, набор `mixed`. Сделайте метод `next(...)` в `FPDecimalFloatBenchmark` package-private (уберите `private`) и добавьте рядом драйвер:

```java
package io.github.maxmorozov.decimal;

import java.util.Random;

public class PrintAsm {
    public static void main(String[] args) {
        Random rnd = new Random(42);
        FPDecimal[] data = new FPDecimal[4096];
        for (int i = 0; i < data.length; i++) {
            long[] v = FPDecimalFloatBenchmark.next("mixed", rnd);
            data[i] = new FPDecimal(false, v[0], (int) v[1]);
        }
        float sum = 0;
        for (int rep = 0; rep < 500; rep++) {          // ~2 млн вызовов: хватит и для C1, и для C2
            for (FPDecimal d : data) {
                sum += d.toFloat();
            }
        }
        System.out.println(sum);                       // чтобы цикл не вырезали
    }
}
```

Если нужно ещё и `toDouble`, добавьте второй такой же цикл и прогрейте его отдельно.

## Как печатать ассемблер

Печатайте не `roundFloat`, а корневой метод, в который он инлайнится:

```
-XX:+UnlockDiagnosticVMOptions
-XX:CompileCommand=print,io.github.maxmorozov.decimal.FPDecimal::toFloat
```

Прежние листинги показывали `roundFloat` как отдельную функцию. Она там оказалась отдельным nmethod, потому что вы печатали именно её, но в бенчмарке она встроена в `toFloatNanosHi`/`toFloatNanosLo` и в `toFloat`. Код там другой: нет пролога, нет передачи аргументов, часть операций сливается с соседним кодом. Мерить нужно то, что исполняется в итоге.

В выводе берите последний `Compiled method (c2)`. До него будут компиляции C1 (уровни 1–3) и, возможно, OSR-версии цикла в `PrintAsm.main`.

## Как проверить, что профиль полный

- Добавьте `-XX:+PrintCompilation` и посмотрите, нет ли после начала измеряемой части строк `made not entrant` для `FPDecimal::toFloat`. Они означают деоптимизацию: какая-то ветка попала в ловушку, а прогрев о ней не знал.
- В листинге поищите `UncommonTrapBlob`. На горячем пути их быть не должно, кроме обычных проверок (null, границы массива). Если остались ловушки на ветках округления или остатка, значит, данные чего-то не покрыли. Тогда добавьте нужный вид значений.
- Если вывод печатается несколько раз за один запуск, это нормально: это перекомпиляции.

## Для бенчмарка то же правило

JMH запускает каждое значение `@Param` в отдельном форке со своим профилем. На `integers` или `lo_mid` C2 увидит один вид данных и срежет всё лишнее, а на `mixed` получится код, ближайший к продакшену. Поэтому цифры для решения нужно брать с `mixed`, а остальные наборы использовать для понимания, где какой путь стоит дороже.
