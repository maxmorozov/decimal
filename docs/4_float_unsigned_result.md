Оставьте v1 (63 бита), v2 не нужна. Я ошибался, когда писал, что интринсик, возможно, поможет: ассемблер показывает, что в вашем JDK он делит медленнее, чем v1.

## Что в ассемблере

**v1** — деление на константу сведено к умножению:

```
movabs rax, 0x112e0be826d694b3   ; магическая константа
imul   rdx                       ; 64x64 -> 128 бит
sar    rdx, 0x11
sub    rdx, r10                  ; поправка знака
imul   r10, rdx, 0x1dcd65        ; q * D для остатка
cmp    r11, r10
```

Тут нет деления и нет ветвлений, только умножения и сдвиги.

**v2** — константа 0x1dcd65 (это 5^9) в `div` подставлена, но настоящего деления на константу не получилось:

```
mov  r10d, 0x1dcd65
cmp  r10, 0            ; проверка знака делителя на каждом вызове
jl   ...
xor  edx, edx
div  r10               ; аппаратное 64-битное деление
```

То есть C2 в вашей версии JDK выбрал `div`, а не умножение на магическую константу. Константность делителя он не использовал, и даже проверка знака делителя осталась в коде (для константы она должна была исчезнуть). На разных процессорах `div r64` стоит по-разному: на старых Intel десятки тактов, на новых Intel и AMD заметно меньше. Версию JDK и модель CPU я не знаю, поэтому на других машинах результат v2 может быть хуже, чем у вас.

Остальной код в обеих версиях практически одинаков: те же сдвиги, те же сравнения для округления.

## Что говорят цифры

| режим | v1 | v2 |
|---|---|---|
| fast_path | 253 | 246 |
| one_step | 265 | 279 |
| two_steps | 282 | 279 |

Различия 3–5%. В `fast_path` деления нет вообще, а v2 всё равно на 3% «быстрее». Значит, уровень шума от расположения кода и инлайнинга не меньше 3%, и на его фоне вывод только один: выигрыша v2 не даёт. На `one_step` v1 даже немного лучше.

Заметьте также, что в абсолютных числах разница между режимами совсем мала: одно значение в `one_step` стоит всего на ~0,1 нс больше, чем на fast path. Видимо, независимые итерации хорошо перекрываются в конвейере, и в этом бенчмарке важна пропускная способность, а не задержка деления. В реальном коде, где деление лежит на критическом пути, `div` будет заметнее.

## Вывод и что почистить

1. Возьмите v1. В v2 к тому же остались устаревшие комментарии (`NORM_BITS_F = 64 // |W'| = 63 bits`, «42 or 43 bits», `floor(2^62 / D)`), которые теперь не нужны.
2. `main` с `FPDecimal` в `FPRounding` — отладочный код для печати ассемблера. Уберите его перед коммитом: `bigmath` не должен зависеть от `decimal`, а `FPDecimal` уже зависит от `bigmath`.
3. Если когда-нибудь будете переходить на новый JDK, повторите замер: возможно, там беззнаковое деление на константу уже превращается в умножение. Заранее на это рассчитывать я бы не стал.

## Необязательная идея: убрать ветки округления

В обоих листингах видны два `uncommon trap` на проверках `rem == half` и `sticky`. Бенчмарк ни разу не попал в ничью, поэтому C2 заменил эти ветки ловушками. Первая настоящая ничья в продакшене вызовет деоптимизацию и перекомпиляцию. Это безвредно, но вызывает разовую паузу. Округление можно сделать без ветвлений: прибавить к `q` поправку и сдвинуть.

```java
// round-half-even с sticky: add = half - 1 + (m_нечётное | sticky)
long half = 1L << (drop - 1);
long add = half - 1 + (((q >>> drop) | (sticky ? 1 : 0)) & 1);
long m = (q + add) >>> drop;
```

Проверка всех случаев (`rem` — отбрасываемые биты `q`, `m` — младший бит мантиссы):

- `rem < half`: `rem + add ≤ 2·half − 1`, переноса нет, округление вниз.
- `rem > half`: `rem + half − 1 ≥ 2·half`, перенос есть, округление вверх.
- `rem == half`, нет sticky: `rem + add = 2·half − 1 + (m&1)`, вверх только при нечётном `m`. Это и есть half-even.
- `rem == half`, sticky: `add = half`, `rem + add = 2·half`, вверх. Это правило «чуть выше середины».
- `rem < half`, sticky: `add = half`, `rem + half < 2·half`, вниз.

Переполнения нет: `q < 2^44`. Перенос в `m == 2^24` обрабатывается так же, как и раньше. Выигрыша в скорости я не обещаю: в вашем бенчмарке ветки идеально предсказуемы, и результат, скорее всего, будет в пределах шума. Смысл правки в том, чтобы не зависеть от профиля прогрева. Если решите её применить, достаточно прогнать готовые тесты (`floatTies`, `roundingCarry`, `randomByBitLength`), они покрывают каждый из пяти случаев.
