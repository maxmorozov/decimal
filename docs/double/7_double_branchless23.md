## Как JIT компилирует `((h0 << 1) << (63 - t))`

Ответ есть в вашем ассемблере `integers_double.asm` (V5 использует тот же код сдвигов). Нужный кусок:

```
shl   rdx, 0x16        ; hi << 22
shr   rcx, 0x2a        ; lo >>> 42
or    rdx, rcx         ; h0
shrx  rbp, rdx, rdi    ; h = h0 >>> t
shl   rdx, 1           ; h0 << 1
...
mov   r10d, 0x3f
sub   r10d, edi        ; 63 - t
shlx  r10, rdx, r10    ; (h0 << 1) << (63 - t)
or    rsi, r10         ; l = (l0 >>> t) | ...
```

- `h0 << 1` стало одной инструкцией `shl rdx, 1`.
- `63 - t` стало парой `mov r10d, 0x3f` и `sub r10d, edi`.
- Переменный сдвиг пошёл в `shlx`: это BMI2, она берёт счётчик по модулю 64, как и Java.

То есть двойной сдвиг стоит ровно одну лишнюю инструкцию (`shl rdx, 1`), и она не лежит на критическом пути: `h0 << 1` считается параллельно с `t`, а `shlx` ждёт более долгую из двух ветвей (`63 - t`, которая зависит от `lzcnt`). Всего в функции порядка 80 инструкций.

## Есть ли смысл в L = 23

Да, правда небольшая. С L = 22 для W ≥ 2^53 получается `t ∈ [0; 39]`, и при `t = 0` выражение `h0 << 64` Java превратила бы в `h0 << 0`, то есть подмешала бы `h0`. Поэтому сдвиг и разбит на два. С L = 23 `t = sh + 23 ∈ [1; 40]` для той же области W ≥ 2^53 (для `b = 54` получается `t = 1`), нуля нет, и сдвиг один: `h0 << (64 - t)` со счётчиком в `[24; 63]`. Остальные константы меняются только в литералах (`hi << 23`, `lo >>> 41`, маска теперь до 40 бит, `W << 23` до 116 бит).

Область применимости у обоих вариантов одна: W ≥ 2^53 (у L = 22 при `b = 53` `t` уже отрицателен, у L = 23 при `b = 53` `t = 0` и сдвиг даёт неверный результат). Поэтому Clinger-порог `2^53` менять не нужно.

Новый метод `toDoubleNanosFlatBranchless23` проверен против `BigDecimal` на 1,89 млн значений (W ≥ 2^53, включая границы `2^b ± 2`, ничьи, переносы), расхождений нет.

Ожидаемый выигрыш: одна инструкция из ~80, то есть порядка 1%, вне критического пути. Скорее всего, вы его не измерите: разброс расположения кода между версиями сопоставим. Но менять стоит: код короче и проще, а риска нет.

## Тот же вопрос про float

В `toFloatNanosFlatMask` была такая же конструкция: `(loN >>> 1) >>> (63 - zz)`. Здесь двойной сдвиг не нужен вовсе: при `hi ≠ 0` имеем `hi < 2^29`, значит, `zz ≥ 35` и `64 - zz ∈ [1; 29]`, а при `hi == 0` слово `loN` нулевое, и результат сдвига не важен. Я добавил `toFloatNanosFlatMask1` с одним сдвигом `loN >>> (64 - zz)` и проверил на 3,18 млн значений, расхождений нет.

## Что делать

Берите `toDoubleNanosFlatBranchless23` и `toFloatNanosFlatMask1` вместо прежних, а `Branchless` и `Mask` из итогового кода уберите. Тесты через `FPDecimal` покрывают оба, но если захотите явную защиту от будущей правки констант, добавьте проверку границ: `W = 2^53` и `W = 2^53 + 1` для double (`t = 1`) и `W = 2^63`, `W = 2^64 − 1` для float (`hi == 0`, `zz = 0` и `zz = 1`).
