`toDoubleNanosHiFlat` (V4) выигрывает почти везде, и для double я бы брал именно её.

## Результаты

| набор | V1 | V3 | V4 (Flat) | V4 против V3 |
|---|---|---|---|---|
| hi_left | 4,64 | 4,67 | 4,67 | 0% |
| hi_right | 4,28 | 4,19 | 4,56 | +8,7% |
| hi_both | 12,37 | 6,89 | **4,50** | **−35%** |
| integers | 8,53 | 7,61 | 6,92 | −9% |
| ties | 13,37 | 5,13 | 4,94 | −4% |
| mixed | 14,56 | 10,77 | 10,09 | −6% |

- **`hi_both` у Flat равен `hi_left` и `hi_right`** (4,5 нс), то есть вся надбавка за непредсказуемую ветку по знаку `sh` исчезла. У V3 она была около 2,3 нс, у V1 около 7,9.
- **Цена на предсказуемых данных намного ниже, чем я ожидал.** На `hi_left` ничего, на `hi_right` +0,37 нс. Прогнозировал около +1 нс, и этот прогноз не оправдался.
- **Единственное место, где V3 лучше, это `hi_right` (+8,7% у Flat).** Если ваши значения почти всегда одного большого порядка (W от 77 до 93 бит), выигрыш Flat пропадает. Если порядки смешаны (как в двух ваших примерах), Flat выигрывает много.

## Что осталось дорогим

`integers` (6,9 нс) и `mixed` (10,1 нс) всё ещё заметно выше `hi_*` (4,5 нс). Это не округление, а ветки выбора пути в `FPDecimal.toDouble()`: сначала `hi == 0`, потом `lo ≤ 2^53`. Данные в `integers` перемешаны по трём классам (Clinger, `lo`, `hi`), и каждая ветка почти случайна. По порядку величин это около 3 нс на значение. Остальное в этих наборах уже оптимально.

## Что можно ещё попробовать

Я добавил в `FPRoundingDouble.java` метод **`toDoubleNanosFlat(hi, lo)`**, который с той же плоской нормализацией (сдвиг влево на 22, потом вправо на `t = sh + 22 ∈ [0; 39]`) обрабатывает любое W > 2^53, в том числе `hi == 0`. Проверил на 3,07 млн значений против `BigDecimal`, расхождений нет. Тогда остаётся одна ветка «Clinger или нет» вместо двух:

```java
if (hi == 0 && Long.compareUnsigned(lo, FAST_MAX_SIG_D) <= 0) {
    v = (double) lo / 1e9;
} else {
    v = FPRoundingDouble.toDoubleNanosFlat(hi, lo);
}
```

Цена: значения класса `lo` пойдут не через `compute_float` (3,09 нс), а через общий путь (около 4,5 нс), то есть на ~1,4 нс дороже. Выигрыш: на данных с перемешанными классами меньше промахов. Если в ваших данных `lo`-класс редок, это явный плюс, если частый и стоит в потоке отдельными группами, нет. Замерьте `lo`, `integers`, `mixed` и `hi_both` и сравните с текущим V4.

## Итог для double

1. **Основной вариант:** `toDoubleNanosHiFlat`.
2. **Опционально:** `toDoubleNanosFlat` с одной веткой. Берите, только если на `mixed` и `integers` он даст заметный выигрыш и это соответствует вашим данным.
3. **Не нужны:** `toDoubleNanosHi` (V3), `toDoubleNanosHiBranchless`, `toDoubleNanosHiLazy`, `toDoubleNanosLo`. Из итогового кода их можно убрать, если останется Flat.

И не забудьте повторить замер для float с большим `N`: там возможна такая же картина, особенно для ветки `lo ≥ 2^63` и выбора класса.
