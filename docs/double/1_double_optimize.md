После переделки генерации картина изменилась, так что часть моих прошлых выводов надо пересмотреть. Нового варианта (V5) я только проверил на корректность (3,3 млн значений против `BigDecimal`), по скорости он не измерен.

## Что показывает ассемблер

В V1 (`FPDecimal`) решение об округлении принимается ветками: `cmp r13, rcx; jg` (`rem > half`), затем `cmp; jne` (не ничья). Вычисление остатка деления (`imul 0x1dcd65; sub; test; setne; or`) стоит только в редкой ветке ничьей. В V3 те же операции выполняются для каждого значения, и в основном пути лишних инструкций около восьми (второй `imul`, `sub`, `setne`, `or`, `movsxd`, `and`, `add`).

Для `integers` объяснение простое. У целого W (то есть при `nanos == 0`) частное `q = W'/D` делится на `2^9`, поэтому отбрасываемые биты `rem` равны нулю. В V1 ветка `rem > half` никогда не срабатывает, предсказывается идеально, и нужен минимум инструкций. V3 делает всю арифметику зря. Это не свойство «целых сумм вообще» (`units`-значения с копейками уже не дают нулевой остаток), а особенность точных целых.

Любопытно другое: у V1 `jg` в `mixed` должна часто ошибаться (при случайных `rem` это почти подбрасывание монеты), а V1 при этом быстрее V3. Либо предсказатель на Zen 5 запоминает повторяющуюся последовательность из 4096 значений, либо промахи дешевле, чем восемь лишних инструкций в окружении дешёвых значений. Чтобы отличить, увеличьте `N` до 65 536 или 262 144: если V1 на `hi_both` и `mixed` заметно подорожает, было запоминание.

## Новый вариант V5: округление «вверх, потом починить ничью»

Идея: главный путь без `sticky` вообще, а ничья исправляется в редкой ветке.

```java
long half = 1L << (drop - 1);
long m = (q + half) >>> drop;                            // half up: rem >= half rounds up
if ((q & ((half << 1) - 1)) == half                      // exact tie in q (rare)
        && !sticky && cur == q0 * D5_9                   // nothing dropped, remainder is zero
        && (m & 1) != 0) {                               // rounded up to odd -> round to even
    m--;
}
```

Основной путь — одно сложение и один сдвиг, как у V3 без цепочки `sticky`, а остаток считается только внутри редкой ветки (в V1 C2 сам отнёс его туда, это видно в листинге). Метод `toDoubleNanosHiLazy` лежит в `FPRoundingDouble.java`, я проверил его на тех же 3,3 млн значений: расхождений нет. Ожидаю, что он сойдётся с V3 на `hi_*` (нет ветки по `rem > half`) и с V1 на `integers`, но это предположение. На `ties` у V5 будет та же непредсказуемая ветка, что у V1, поэтому там V3 останется лучше. В реальных данных ничьи редки, а `ties` в бенчмарке искусственно превращает их в 2/3 значений.

2. Для float та же идея применима (`roundFloat` в V3), и стоит проверить её там, раз `integers` у V3 для float тоже был хуже V1.
